qwen serve

Turning a terminal coding agent into a daemon you can reach from a browser, a phone, or another machine.

Qwen Code v0.25.1stage 1 experimentalflag: --http-bridge

The problem

Your agent lives in a terminal

What that costs you

  • Tied to one window on one machine
  • Close the laptop lid → the run dies
  • No way to watch a long job from elsewhere
  • Nothing to script against
  • One session, one user, one SSH tab

What qwen serve gives you

  • An HTTP daemon with a real API
  • A browser UI (the Web Shell)
  • Sessions that survive a page refresh
  • Access from a phone on the same network
  • Many concurrent sessions
One command changes the deployment shape: qwen is a process you watch. qwen serve is a service you talk to.

Architecture

What actually starts

you │ ┌─────────┴──────────┬─────────────────────┐ │ │ │ browser curl / script another qwen (Web Shell) (HTTP + SSE) (--join / Agent Host) │ │ │ └────────────────────┴─────────────────────┘ │ ┌─────────▼──────────┐ │ qwen serve │ daemon :4170 │ ─ HTTP API │ bearer token (non-loopback) │ ─ Web Shell UI │ CORS allowlist │ ─ session store │ SSE replay ring └─────────┬──────────┘ │ --http-bridge (stage 1) ┌─────────▼──────────┐ │ qwen --acp child │ the real agent runtime │ tools, MCP, skills│ one per session └────────────────────┘
Stage 1 spawns a child process per session. The help text is explicit that stage 2 native in-process mode is not yet implemented, and --http-bridge will become opt-in then. Treat the internals as moving.
Security — the most important slide

Loopback is trusted. Everything else is not.

Bind 127.0.0.1 default

Auth-free by design. Only processes on your machine can reach it.

qwen serve

Bind anything else token required

A LAN IP requires a bearer token. With neither --token nor QWEN_SERVER_TOKEN, one is generated at startup.

qwen serve --hostname 192.168.1.20
Read the help text carefully: "Loopback (127.0.0.0/8, localhost, ::1, [::1]) is auth-free; anything else requires a token." An agent that can run shell commands, exposed on your network without a token, is not a small mistake. --require-auth forces a token even on loopback — use it on shared dev boxes and CI runners, where any local user can hit 127.0.0.1.
Security, continued

Three settings that bite people

--allow-origin

Browser clients send an Origin header. If it is not on the allowlist the daemon 403s every request — including all the ones from your phone.

--allow-origin \
  http://192.168.1.20:4170

--tls-cert / --tls-key

Browsers only allow the microphone on a secure context. Over a LAN IP that means HTTPS, or voice input silently does not work.

# mkcert makes a local cert
--tls-cert cert.pem \
--tls-key key.pem

--enable-session-shell

Turns on direct POST /session/:id/shell — arbitrary command execution over HTTP. Off by default. Leave it off unless you have a real reason.

A real trade-off

--local-control vs a static token

--local-control

  • Shares the Web Shell on your LAN
  • Mints its own revocable pairing token
  • Prints a QR code in the terminal
  • Best-effort sleep inhibition
  • Settings card can turn it off while the daemon lives

But: the pairing token is minted in memory and revoked at stop. Restart → new token → every bookmarked URL breaks.

Static bind

qwen serve \
  --hostname 192.168.1.20 \
  --token "$QWEN_SERVER_TOKEN" \
  --allow-origin http://192.168.1.20:4170
  • Token comes from you, so it survives restarts
  • Bookmark http://IP:4170/#token=… once, forever
  • No QR — you manage the secret yourself
Rule of thumb: ad-hoc demo to a room → --local-control and scan the QR. Persistent setup you will come back to → static token. Also note --open hands a token-bearing URL to the browser launcher, which is visible in the process list — open it manually on a multi-user host.
Sessions

Sessions outlive your browser tab

The Web Shell talks to the daemon over Server-Sent Events. Drop the connection, reconnect, and it replays what you missed:

GET /session/:id/events
Last-Event-ID: 4182        ← resume from here

The replay ring

--event-ring-size (default 8000) is how much history a reconnect can recover. Bigger = more headroom, a few hundred KB extra RAM per session.

Late attach

POST /session/:id/load hands a joining client a compacted snapshot. --compacted-replay-max-bytes caps it (max 256 MiB).

This is the feature that makes it feel like a real service rather than a toy. Refresh the page on your phone mid-run and you are back where you were.
Limits

It refuses work rather than dying

flagdefaultwhat it protects
--max-sessions32Concurrent live sessions; beyond it, new spawns get 503. Attaching to existing ones still works.
--max-total-sessions—Same cap across all workspace runtimes.
--max-pending-prompts-per-session5Queued prompts per session; excess get 503.
--max-connections256Raw TCP sockets. Slow or phantom SSE clients are rejected at accept time.
--prompt-deadline-ms—Server-side wallclock cap on a prompt.
--mcp-client-budget—Live MCP clients per workspace. --mcp-budget-mode chooses warn / enforce / off.

0 disables a cap. Note the difference between warn (observability only) and enforce (refuses) — boot rejects enforce without a budget set.

Memory

A budget, not a hope

--memory-budget-mb

Total budget for the daemon process tree. Unset, it is derived as 50% of cgroup-constrained or host memory, capped at available memory. Range 1024–1048576.

Also sizes a daemon-wide pool of 5% of the budget (capped at 1024 MB) for replay growth.

--memory-pressure-mode

observe (default) reports the level and raises a status issue when it leaves normal. off reports figures but raises nothing. Nothing remediates in either mode.

--child-heap-mode

observe models a per-child partition and counts spawns that would have exceeded it. admit rejects starts past the limit. enforce is experimental.

A refusal count of 0 does not mean the partition would be safe to apply.

Why this matters on a laptop

Each session is a child process with its own V8 heap. Thirty-two sessions is thirty-two heaps. On a 16 GB machine that is the difference between a demo and a freeze.

Workspaces

More than one project, more than one machine

Multiple workspaces

qwen serve --workspace /repos/api --workspace /repos/web

Repeat the flag to register isolated runtimes; the first is primary. A POST /session with a mismatched cwd returns 400 workspace_mismatch — it will not let a session wander into the wrong project.

Linking machines

--join

Join another Qwen Code as a runtime, using the one-line link from Agent → Runtime → Add runtime. Your laptop becomes a worker for someone else's daemon.

Agent Host

--agent-host-server, --agent-host-workspace-id, --agent-host-name register this daemon as a host with a primary. --agent-host-allow-http permits unencrypted connections — trusted demo networks only.

--memory-project-scope picks how project memory is partitioned: workspace (default, isolated) or git-root (legacy shared).

Recipes

Four ways to run it

1 · Local development

qwen serve                    # loopback, no token, Web Shell on :4170

2 · Phone on the same Wi-Fi, ad-hoc

qwen serve --local-control     # prints a QR — scan it

3 · Phone, persistent (survives restarts)

qwen serve \
  --hostname 192.168.1.20 \
  --token "$(cat ~/.qwen-serve-token)" \
  --allow-origin http://192.168.1.20:4170

4 · Shared dev box or CI

qwen serve --require-auth --no-web --max-sessions 4
# token enforced even on loopback; API only; small session cap
Live demo

What we will actually run

  1. Start it. qwen serve — note the printed URL, note that no token was needed on loopback.
  2. Open the Web Shell in a browser. Start a session against the local model.
  3. Kill the network. Turn off Wi-Fi mid-run, reconnect, and watch the SSE ring replay what you missed.
  4. Phone. Re-run with --local-control, scan the QR, drive the same daemon from a handset.
  5. Prove the token. Re-run on a LAN IP and show the 401 without Authorization, then success with it.
  6. Show the ceiling. --max-sessions 2, open a third, read the 503.
Every step above is a behaviour you can read off --help. Nothing requires a GPU, a cloud account, or a model bigger than the 1.7B you already downloaded.
Fit for purpose

What to use, and what to leave alone

Show these

  • Loopback vs LAN auth model
  • Web Shell + phone access
  • SSE replay surviving a refresh
  • --max-sessions returning 503
  • --workspace isolation
  • --local-control QR pairing

Skip these

  • --profile hosted-harness + capability digests
  • Agent Host control-plane wiring
  • --experimental-paired-engines
  • --child-heap-mode enforce
  • --enable-session-shell
  • Journal byte-cap tuning
The left column is durable and easy to demonstrate. The right column is private, experimental, or explicitly documented as not-yet-implemented — teaching it would be teaching something that will not survive to next semester.
Takeaways

Five things to remember

  1. qwen serve turns an agent from a process into a service.
  2. Loopback is auth-free; every other bind needs a token. That single rule is the security model.
  3. A static token survives restarts. A --local-control pairing token does not.
  4. Sessions are durable because of the SSE replay ring — that is why a refresh does not lose your work.
  5. It is stage 1 experimental. The API shape is real; the internals will move.
