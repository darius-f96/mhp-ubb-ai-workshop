Self-hosted LLMs

Running your own models, on your own machine, and knowing exactly what that costs you.

1h 40m16 GB laptopno GPU required

Why bother

You could just call an API

And you would get a better model than anything your laptop can run. So why not?

ReasonWhat it means in practice
PrivacyYour code and documents never leave the machine. Often not a preference — a legal requirement.
CostZero marginal cost per token. An API bill grows forever; a laptop you own does not.
No rate limitsNothing throttles you at 3 a.m. Run 10 000 documents through an embedder and pay nothing.
AvailabilityWorks on a plane, in a basement, at a venue with broken Wi-Fi. The model is a file.
ControlExact weights, exact quantisation, exact context window. You can fine-tune.
UnderstandingOnce you have watched a 1.7B model fail at tool calling, you know what you are buying — and what you give up.
The honest counter-argument

A local small model is worse

It will be

  • slower
  • dumber
  • confidently wrong

So self-hosting is

a trade, not an upgrade.

Knowing when the trade is worth it is the actual skill. That is what today is for.

Everything after this slide is about making the trade deliberately instead of by accident.
The mental model

Five layers

Every tool today lives in exactly one box. If you remember one slide, remember this one.

Build order

You do not need all five

Minimum working setup

Layers 1, 2 and 5 — a model file, an engine, and something to talk to it.

weights → llama.cpp → curl

Layers 3 and 4 are conveniences

They pay off once you have more than one model or more than one client.

Adding a layer you do not yet need is how people end up debugging a proxy at 2 a.m. for a model they could have run directly. Build bottom-up, and verify each layer before adding the next.
Layer 1 · weights

A model is a file of numbers

Genuinely all it is: a large tensor of floating-point parameters, plus metadata describing how to arrange them.

safetensors

The native format. Full precision, large. Needs PyTorch or vLLM to run.

GGUF ← what you will use

One self-contained file for llama.cpp: weights plus the tokenizer plus the chat template. Usually quantised.

Where they come from

Hugging Face is the de facto registry — think npm or Docker Hub, for models. Also: Ollama's library, models.dev (for API models), vendor sites.

Layer 1 · quantisation

Compressing the numbers

A model trained at 16 bits per weight can run at 4 bits with modest quality loss — 4× smaller, and on a CPU often faster, because you move less data.

SuffixBitsQualityUse it when
Q8_08Near-losslessYou have RAM to spare
Q6_K6ExcellentGood default on 16 GB
Q5_K_M5Very goodBalancing act
Q4_K_M4Good← the workshop default
Q3_K_M3Noticeably worseDesperate for RAM
Q2_K, IQ2_*2PoorDemos of what quantisation destroys
Rule of thumb: RAM for weights ≈ file size + 10–20%.
Layer 1 · naming

Reading a Hugging Face repo id

ggml-org / Qwen3-4B-GGUF  /  Qwen3-4B-Q4_K_M.gguf
   │           │                    │
 owner      repo                 the file
        (quantised re-uploads
         end in -GGUF)

Who to trust for a GGUF

  1. The model author's own GGUF repo (Qwen/…-GGUF)
  2. ggml-org — the llama.cpp team
  3. unsloth or bartowski — reliable community quantisers
Filenames are case-sensitive and conventions differ: ggml-org uses Qwen3-1.7B-Q4_K_M.gguf while Qwen uses lowercase qwen2.5-coder-1.5b-instruct-q4_k_m.gguf. Copy them exactly — a retyped name is a 404.
Layer 1 · licences

"Open weights" is not one thing

Permissive

Apache 2.0 / MIT. Use commercially, no conditions.

SmolLM, Granite 4.0, nomic-embed, bge, LFM2.5

Qwen licence

Free including commercial, but has an acceptable-use policy and registration terms at very large scale.

Gated

Log in and click through a licence first. hf download fails with 401 until you do.

Meta Llama, Mistral Ministral

For a workshop, prefer ungated permissive models. No student should spend ten minutes on a licence form — which is one reason Qwen3 and SmolLM are the defaults here.
Layer 2 · engines

llama.cpp vs vLLM

llama.cpp

C/C++, no dependencies. Runs on anything — CPU, Apple Metal, NVIDIA, AMD, a phone. Uses GGUF.

This is the engine for your laptop, and what the whole workshop is built on.

vLLM

Python, built for throughput on GPUs. Headline feature is PagedAttention — it manages KV cache like an OS manages virtual memory, so it batches many concurrent requests efficiently.

On a CPU it is not worth your time. The image alone is 10.31 GB.

llama.cppvLLM

The most important slide

The OpenAI-compatible API

A de facto standard: a couple of HTTP endpoints with a known JSON shape.

curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3-1.7b",
    "messages": [{"role":"user","content":"Say hello in one word."}]
  }'
Because llama.cpp, vLLM, LiteLLM, llama-swap and Ollama all speak it, any client works with any server. Your coding agent does not know or care whether the model behind that URL is a 1.7B file on your laptop or a frontier model in a data centre.

Swap the URL, keep the tool.
Layer 2 · endpoints

The ones you will actually use

EndpointPurpose
GET /v1/modelsWhat is available. Your first debugging tool — if this fails, nothing else will work.
POST /v1/chat/completionsChat, and tool calling. The main one.
POST /v1/embeddingsText → vectors, for search and RAG.
POST /v1/rerankRe-score search results.
GET /healthIs it up?
For the rest of today, whenever something does not work, the first question is always:
can I curl /v1/models on it?
Layer 3 · managers

You have one slot and several models

Loading a model takes seconds and costs gigabytes. Four llama-server processes competing for 16 GB is not going to work.

llama-swap

Presents one API and starts/stops engines behind it on demand. Ask for model A, it boots A. Ask for B, it unloads A and boots B. Idle models die after a TTL and your RAM comes back.

:8090 ──┬──> llama-server (chat) ← loaded now ├──> llama-server (coder) ← starts on demand ├──> llama-server (embed) ← starts on demand └──> llama-server (tiny) ← starts on demand

This is what makes a specialised local setup practical — and specialisation is how small models become genuinely useful.

Layer 4 · gateways

Several backends, one endpoint

You have your local llama-swap, maybe a colleague's GPU box, maybe OpenRouter, maybe Google's free tier. Different URLs, different keys.

LiteLLM puts one endpoint in front of all of it

  • Routing — fast-model local, big-model cloud
  • Fallback — local died? Retry on the cloud. This is what makes a workshop survivable.
  • Keys and budgets
  • Uniform API — 100+ providers behind OpenAI-shaped endpoints
Clients talk to :4000 and never learn where the tokens came from.
Layer 5 · clients

The point of all this

Qwen Code

Alibaba's terminal agent. Reads your repo, edits files, runs commands.

Has a qwen serve mode that turns it into a daemon with a browser UI.

OpenCode

Similar terminal agent, provider-agnostic by design. Ships a model catalogue so hosted providers need no config.

Both are configured by giving them a base URL and a model name. Point them at http://127.0.0.1:4000 and they use whatever LiteLLM routes to.

Configuring both takes ten minutes and teaches the real lesson: the stack is the durable investment, the client is interchangeable.
Concepts · tokens

Models do not see words

They see tokens — chunks of text. Everything is measured in them: context size, price, speed.

Mental model

1 token ≈ 4 characters ≈ 0.75 English words

# 19 characters ≈ 5 tokens
echo -n "The quick brown fox" | wc -c

A 500-word document is roughly 650 tokens. A large source file can be 3 000. This is why context runs out faster than you expect.

Concepts · context

The context window

The maximum tokens the model can attend to at once — your prompt + its reply + the whole conversation so far.

Exceed it and the start silently falls off the front. There is no error. The agent just forgets what you told it twenty messages ago.

This is the hardest constraint on a laptop

Context is not free. The engine allocates a KV cache that grows linearly with context size.

A model file is 1.3 GB. At a 128k context, the KV cache can be larger than the model.

Default small. Start at -c 4096 and raise it only when you hit the wall.

Concepts · context, measured

Two traps, measured not guessed

1 · -c 0 means "the model's own context", not zero

That is the default. On a 128k model it allocates a 128k KV cache and takes your laptop with it. Always set -c explicitly.

2 · Parallel slots eat your context

Measured on llama.cpp build 9761, same model each run:

Flagsn_ctx_seqWhat happened
-c 4096 (auto)4096auto enables a unified KV cache; slots share one pool
-c 4096 -np 14096one slot, full context
-c 4096 -np 41024explicit parallel divides it: 4096 ÷ 4
Typing -np 4 yourself gives each request a quarter of the context you asked for. Want four slots at 4096 each? Ask for -c 16384 -np 4.

For this workshop: use -np 1. You are one person.

Dominated by prefill — processing your prompt. Feels like responsiveness.

Concepts · sampling

Temperature, and a real trap

ParameterDoesUse
temperatureControls randomness0.0–0.3 code and tools · 0.8–1.2 prose
top_pTruncates to a probability massUsually leave at the model's default
top_kTruncates to N candidatesUsually leave alone
The trap: many models have a recommended sampling recipe, and ignoring it degrades quality noticeably. Qwen3 in particular wants specific settings, and its thinking mode should often be disabled for tool use.

Read the model card. It is not boilerplate.
Concepts · reasoning

Thinking models, and the empty reply

Some models emit a private chain-of-thought before answering. Better on hard problems — and it costs a lot of tokens.

A thinking model can burn 4 000 tokens of reasoning to write 200 words of answer.

Two consequences on a laptop

  1. It is slow.
  2. If max_tokens is too small, it spends the entire budget thinking and returns an empty reply.
That looks exactly like a crash, and it is not. Check .choices[0].message.reasoning_content — if that is huge and content is empty, raise max_tokens or pass --reasoning-budget 0.
Concepts · agents

Tool calling — what makes an agent

model ──> {"tool":"read_file","args":{"path":"main.py"}} your code runs it model <── {"result":"def main(): ..."} model ──> next step

The model emits structured JSON saying "call this function with these arguments"; your code runs it and feeds the result back. That loop is what turns a chatbot into an agent — and it is what makes coding CLIs work.

It is also the first thing that breaks on small models. Reliable tool calling needs a big model. A 1.7B fumbles the JSON; a 4B is marginal; expect 7B+ for dependable agents.

llama.cpp requires --jinja so the model's own tool-call template is used — in current builds it is on by default.

Concepts · RAG

Retrieval-Augmented Generation

Instead of hoping the model knows something, you look it up and put it in the prompt.

documents ─> chunk ─> embedding model ─> vectors ─> store query ─> embedding model ─> vector ─> nearest neighbours ─> top-k chunks top-k chunks + query ─> chat model ─> answer (with citations)
Every piece of that runs locally on your laptop, and the embedding models are tiny — nomic-embed-text-v1.5 is 0.15 GB.

RAG is the highest-value thing you can self-host: a small model plus good retrieval beats a big model guessing.
Setting expectations

What small local models are actually good for

Genuinely good

  • Embeddings and retrieval — tiny models, excellent results, zero cost
  • Classification and extraction — "is this spam?", "pull the dates out"
  • Summarisation of short documents
  • Anything private — it never leaves the machine
  • Learning — you cannot understand these systems without running one

Genuinely bad

  • Correct code across many files
  • Reliable tool calling
  • Long reasoning chains
  • Anything needing current facts
For the second column, the stack you build today routes to a cloud model. That is a feature, not a cop-out.
What good looks like

Your target by the end of the day

your coding agent ──> LiteLLM :4000 ──> llama-swap :8090 ──> llama-server ──> Qwen3-1.7B.gguf │ └──fallback──> a cloud API (when local is not good enough)

How to build it

  1. One layer at a time, bottom-up
  2. Verify each layer before adding the next — every layer has a curl
  3. When it breaks, work down the stack, not up
./scripts/healthcheck.sh   # tells you the LOWEST broken layer

Takeaways

Five things to remember

  1. Five layers. Build bottom-up, verify each one.
  2. The OpenAI-compatible API is why any client works with any server.
  3. Context costs RAM, and -np divides it. Quantisation costs quality.
  4. Tool calling breaks first as models shrink — and agents are built from tool calls.
  5. Self-hosting is a trade. RAG and private work win; frontier reasoning does not.
